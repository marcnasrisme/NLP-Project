1. The recipe in one sentence

Yes — your description is exactly right. We compute next-token logits using the effective weight $W + \sum_k \alpha_k \, B^{(k)} A^{(k)}$ at every projection in every layer, score those logits against the gold continuation, and back-propagate the loss only through the routing classifier (which produces the $\alpha$ values). The base $W$ and the experts $A^{(k)}, B^{(k)}$ all stay frozen — only the small classifier learns.

2. Forward pass on "Oh no, I lost my job"

Let's pick a concrete training pair from EmpatheticDialogues:

prompt: "Oh no, I lost my job" ← 7 tokens target: "I'm so sorry to hear that" ← 7 tokens (the gold assistant response) full seq: prompt + target ← 14 tokens, T = 14

Step 2.1 — Embedding

Tokenize and look up:

$$ h^{0} = E[\text{token\_ids}] \in \mathbb{R}^{T \times d}, \qquad T = 14, \, d = 4096. $$

Step 2.2 — One forward pass through 32 X-LoRA-active layers

For each layer $\ell = 1, \dots, 32$:

  1. The classifier reads the current hidden state $h^{\ell-1}$ and produces routing weights $\alpha_{t, \ell} \in \Delta^3$ for every token at this layer (this is the per-(token, layer) granularity X-LoRA gives by default — for our purposes, conceptually identical to "produce $\alpha_t$ once").
  2. For each LoRA target projection $W_Q^\ell, W_K^\ell, W_V^\ell, W_O^\ell$, the effective weight applied at token $t$ is:
$$ W_{Q,\text{eff}}^{\ell, t} = W_Q^\ell + \sum_{k=0}^{3} \alpha_{t, \ell, k} \, B_Q^{(k, \ell)} \, A_Q^{(k, \ell)}. $$
  1. Standard self-attention + FFN with these effective weights produces $h^{\ell}$.

Notice: $\alpha$ enters multiplicatively into the layer's matmul. Because $\alpha$ comes from the trainable classifier, and $\alpha$ touches every layer's output, the loss gradient will flow back through every $\alpha$ to the classifier.

Step 2.3 — Final logits

After layer 32:

$$ \text{logits}_t = h^{32}_t \cdot E^\top \in \mathbb{R}^{V}, \qquad V \approx 32{,}000. $$

So we have a logit vector for each of the $T = 14$ positions, predicting the next token at each.

3. The next-token-prediction loss, written out

For each position $t$ in the gold response, we want the model to predict the actual next token. The loss is mean cross-entropy only over response tokens (we mask out prompt-position losses):

$$ \mathcal{L}_{\text{NTP}} = -\frac{1}{|\mathcal{R}|} \sum_{t \in \mathcal{R}} \log P_t[y_{t+1}], $$

where:

  • $\mathcal{R} = \{7, 8, 9, 10, 11, 12\}$ — the positions whose next token is a gold-response token (one less than the response length).
  • $P_t = \mathrm{softmax}(\text{logits}_t)$ is the predicted next-token distribution at position $t$.
  • $y_{t+1}$ is the actual next-token id from the gold sequence.

Concretely for our example:

position t token at t target y_{t+1} CE term 0 "Oh" "no" -log P_0["no"] ← masked (prompt) 1 "no" "," -log P_1[","] ← masked 2 "," "I" -log P_2["I"] ← masked 3 "I" "lost" -log P_3["lost"] ← masked 4 "lost" "my" -log P_4["my"] ← masked 5 "my" "job" -log P_5["job"] ← masked 6 "job" "I'm" -log P_6["I'm"] ← FIRST scored 7 "I'm" "so" -log P_7["so"] 8 "so" "sorry" -log P_8["sorry"] 9 "sorry" "to" -log P_9["to"] 10 "to" "hear" -log P_10["hear"] 11 "hear" "that" -log P_11["that"] 12 "that" "<EOS>" -log P_12["<EOS>"] ───────────────────────────────────── Loss = mean of the 7 unmasked CE terms (positions 6..12)

The mask is the same trick used in evaluate._encode_prompt_response — set labels[:7] = -100 so PyTorch's CE skips those positions.

4. The backward pass — what gradient flows where

Now the interesting part. PyTorch's autograd builds a computational graph during the forward pass; loss.backward() walks it in reverse and computes gradients with respect to every leaf tensor that has requires_grad=True.

What's a leaf with requires_grad?

Only the classifier's MLP weights $\theta_g$. Everything else — base $W$, four LoRA experts $\{A^{(k)}, B^{(k)}\}_{k=0}^3$ — has requires_grad=False.

The chain rule, conceptually

The classifier produces $\alpha = g(\cdot ; \theta_g)$. This $\alpha$ enters the effective weight at every layer:

$$ \Delta W^{(\ell)} = \sum_k \alpha_k \, B^{(k, \ell)} A^{(k, \ell)} \quad\Longrightarrow\quad \frac{\partial \Delta W^{(\ell)}}{\partial \alpha_k} = B^{(k, \ell)} A^{(k, \ell)}. $$

Then the chain of dependencies for the gradient with respect to $\theta_g$:

$$ \frac{\partial \mathcal{L}_{\text{NTP}}}{\partial \theta_g} = \sum_{\ell, t, k} \underbrace{\frac{\partial \mathcal{L}_{\text{NTP}}}{\partial \alpha_{t,\ell,k}}}_{\text{loss back through } \ell..32} \cdot \underbrace{\frac{\partial \alpha_{t,\ell,k}}{\partial \theta_g}}_{\text{classifier head}}. $$

The first factor — the gradient of the loss with respect to a single routing scalar at one (token, layer) — requires backward propagation through every transformer layer above it. This is what makes the backward expensive.

What's NOT updated

The autograd machinery still walks through the base model and the LoRA experts during backward, but their weight gradients aren't computed (because requires_grad=False). The activation gradient (gradient of loss w.r.t. each layer's hidden state) is computed and propagated. That's what carries the signal back to the classifier.

Key insight: "frozen" doesn't mean "shortcut around in backward." Activations through frozen layers are still part of the graph. The 7B base + 4 experts contribute essentially the same memory-and-compute cost during backward as they would in full fine-tuning — only the optimizer step is cheaper.

5. Memory cost

This is where it hurts. Let's count carefully.

Parameter memory (constant, on GPU at all times)

WhatSize
Mistral-7B base in FP16$\approx 14$ GB
4 LoRA experts × 16M params × 4 bytes (FP32)$\approx 0.26$ GB
Classifier (4-layer MLP, 2048 hidden, ~16M params, FP32)$\approx 0.06$ GB
Optimizer state (Adam: 2× classifier params)$\approx 0.13$ GB
Subtotal — parameter memory~14.5 GB

Activation memory (the variable, scales with batch × seq length)

For backward to work, every layer's intermediate activations must stay resident until that layer's backward step finishes. Mistral has 32 layers; each layer roughly stores:

  • Residual stream input/output: $T \times d = T \times 4096$ FP16 floats.
  • Attention Q, K, V projections: $3 \times T \times d$.
  • Attention probabilities (softmax output): $T \times T$ per head × 32 heads.
  • FFN intermediate (Mistral uses SwiGLU with intermediate $\approx 14336$): $T \times 14336$.

Adding it up, roughly $\approx 50 \times T \times d \times 2$ bytes per layer. For $T = 256$:

$$ 50 \times 256 \times 4096 \times 2 = 105 \text{ MB per layer}, \quad \times 32 \text{ layers} \approx 3.3 \text{ GB per batch element.} $$

For $T = 512$: $\approx 6.6$ GB per batch element. So with batch size 1, total VRAM is roughly:

Sequence lengthVRAM total (params + activations)Fits on…
$T = 128$$\approx 16$ GBA100 (40 GB) or T4 (16 GB) — tight
$T = 256$$\approx 18$ GBA100, V100 (32 GB)
$T = 512$ (your current)$\approx 21$ GBA100 only

This is the dominant cost. The frozen experts and frozen base contribute zero parameter gradients, but they contribute the full activation footprint.

7. Why 4-bit quantization breaks this — the real reasons

You asked specifically why Q4 doesn't work. The answer is layered.

Reason 1 (the proximate one): PEFT's hard check

Look at inference.py:97-101:

if model_has_bnb_linear(base_model):
    raise ValueError(
        "PEFT X-LoRA is not compatible with this bitsandbytes Linear base path. "
        "Load the X-LoRA base with load_base_model(..., quantized=False, torch_dtype=torch.float16)."
    )

PEFT explicitly refuses to wrap a model whose linear layers are bitsandbytes Linear4bit. This is a software-level check, not a fundamental autograd limitation. PEFT's X-LoRA hooks were never validated against the bnb path.

Reason 2 (the deeper one): the bnb Linear4bit forward path is custom CUDA

A normal nn.Linear does:

output = input @ weight.T + bias    # standard PyTorch matmul, autograd-tracked

A bnb Linear4bit does, roughly:

weight_dequantized = bnb.cuda_kernels.dequantize_nf4(weight_4bit, quant_state)
output = input @ weight_dequantized.T + bias    # the dequantize call is *inside* the kernel

The dequantization step uses a fixed NF4 codebook lookup. It's technically differentiable (bitsandbytes does implement a backward that recovers $\partial \text{loss} / \partial \text{input}$), but:

  1. The weight gradient $\partial \text{loss} / \partial W_{4bit}$ is not computed (and we wouldn't want it to be — we're not training the base). This part is fine.
  2. The activation gradient $\partial \text{loss} / \partial \text{input}$ is computed by re-dequantizing the weight inside the backward kernel. This is what carries the signal back to the classifier, and it does work — but it's numerically imprecise. The quantization error injects noise that compounds over 32 layers of backward.
  3. PEFT's X-LoRA was designed to wrap regular nn.Linear; the LoRA-augmentation logic and classifier hooks assume a clean linear forward. Wrapping a bnb Linear4bit means you'd need a custom adapter path that intercepts before dequantization and applies the LoRA delta to the dequantized weight on the fly. This isn't implemented in the version you have.

Reason 3 (the practical one): you don't save much memory anyway

Q4 saves ~10 GB of parameter memory (14 GB FP16 → 4 GB Q4). But the activation memory — which is the dominant cost during backward, ~7 GB at $T=512$ — is unchanged. The ratio of savings to total memory is modest, and you pay for it with classifier-gradient noise and a coding burden.

The summary: Q4 isn't fundamentally incompatible with NTP-style training; PEFT just doesn't support it, and the gradient quality through dequantization-on-the-fly is poor. The cheap path is to use FP16 throughout. The base model fits in FP16 on an A100; you don't need quantization for VRAM reasons.

8. Mitigations that bring the cost back down

If $T=512$ × batch 1 × A100 is too expensive, several things help:

TechniqueEffectTradeoff
Gradient checkpointing Activations stored only at "checkpoint" layers; recomputed during backward. Cuts activation memory ~4×. ~30% slower per step. One-line addition: model.gradient_checkpointing_enable().
Shorter $T$ Halve $T$ → halve activation memory. Truncates long conversations; mostly fine for ED.
Train on a subset 1024 examples × 2 epochs instead of 2048 × 4. Less robust convergence.
Train only the last K layers' routing Freeze classifier outputs at layers 1–28; only the layer-29..32 routing learns. Loses some expressivity; backward only needs to traverse 4 layers.
Skip the per-layer dimension Set layerwise_scalings=False in XLoraConfig. Routing becomes per-token only. Smaller routing tensor, less memory; aligns with the per-token goal anyway.

The combination "checkpointing + $T=256$ + layerwise_scalings=False" gets you down to maybe 12–14 GB total VRAM and ~1.0 s/step. Comfortable on A100, plausible on a 24 GB consumer GPU.

9. Verdict

QuestionAnswer
Is your description of the training step correct? Yes — forward with effective weight $W + \sum_k \alpha_k B^{(k)} A^{(k)}$, score next-token logits, backprop only through the classifier producing $\alpha$.
Is it viable for DESA? Yes on A100, no on T4 (T4's 16 GB doesn't fit FP16 Mistral + activations together).
How long? ~1–2 hours for a sensible schedule on A100.
Why not Q4? PEFT explicitly refuses; bnb backward gradient is noisy; little memory saved during backward anyway. Use FP16.
Practical recommendation if you decide to do it:
  • Use the FP16 base model (no quantization), exactly as cell 5 of notebook 05 already does.
  • Set layerwise_scalings=False in the X-LoRA config to align with your per-token goal.
  • Enable gradient checkpointing on the base model.
  • Trim $T$ to 256, use a 1024-example × 2-epoch schedule.
  • Loss: standard NTP CE on the gold response only (mask prompt tokens, exactly like evaluate._encode_prompt_response already does).
  • Optimizer: AdamW on classifier params only; everything else stays frozen.
  • Expect ~1 hour on A100 and a measurable drop in PPL on the gold continuation versus your pooled-CE classifier — that's the headline result.
