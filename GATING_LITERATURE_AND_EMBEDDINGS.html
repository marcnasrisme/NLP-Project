Part 1 — Gating in the LoRA-MoE Literature

Your DESA turn-gate uses mean pooling on the last hidden state, followed by a 2-layer MLP and softmax. That's a defensible design but it's not what most published LoRA-mixture papers do. Let's go through them.

1.1 X-LoRA (Buehler & Buehler, 2024)

Source: arXiv 2402.07148, also published in APL Machine Learning (June 2024).

This is the paper that the PEFT XLoraConfig in your inference.py implements. Key design points:

  • Routing granularity: per-token and per-layer. The scaling tensor has shape $(T, L, K)$ — token × layer × adapter, exactly as we covered before.
  • Input to the gate: the gating "scaling head" reads the hidden states from the base model (run with adapters disabled in a first forward pass), then linear FC layers produce the scalings, then softmax is applied across the adapter axis so weights at each $(t, \ell)$ sum to 1.
  • Pooling: none. The classifier is applied per-token — it processes the full $T$-length sequence and outputs a routing distribution at every token.
  • Architecture: the paper itself is intentionally vague — it says "the scaling head can be implemented as a simple feed-forward neural network with one or few layers" and leaves it user-configurable. PEFT's implementation lets you set xlora_depth (number of FC layers) and xlora_size (hidden width). Your config uses depth 4 and width 2048.
  • Training: standard supervised next-token prediction loss with the X-LoRA stack active. The classifier is the only thing that updates — base model and the LoRA experts are frozen.
X-LoRA is anti-pooling. It deliberately does not collapse the sequence dimension because the whole point of token-level routing is to react differently at each position.

1.2 LoRAMoE (Dou et al., 2024)

Source: arXiv 2312.09979.

One of the more influential designs. LoRAMoE inserts multiple LoRA experts at the FFN layer of each transformer block, plus a router per block.

  • Routing granularity: per-token. The router is applied at the FFN of every transformer block.
  • Router formula: dead simple — a linear layer plus softmax:
$$ G(h) = \mathrm{softmax}(h W_g), \qquad h \in \mathbb{R}^d,\ W_g \in \mathbb{R}^{d \times K}. $$
  • Input to the router: the hidden output from the attention sublayer (i.e., the residual stream right before the FFN), evaluated per token. There is no pooling.
  • One router per layer: each transformer block has its own gating matrix $W_g^\ell$.
  • Training loss: task loss (e.g., next-token CE) plus a localized balancing constraint loss
$$ \mathcal{L}_{\text{lbc}} = \frac{\sigma^2(Z)}{\mu(Z)}, \qquad Z = I \odot Q, $$

where $Q$ is an importance matrix capturing router weight per expert per sample, and $I$ assigns higher importance ($1+\delta$) when an expert's designated type matches the training sample. This pushes experts to specialize within groups while keeping load balanced. Crucially, this auxiliary loss is what prevents the gate from collapsing to uniform — the exact failure mode your X-LoRA classifier suffers from.

1.3 MoLE (Wu et al., ICLR 2024)

Source: arXiv 2404.13628.

  • Routing granularity: per-layer (one gate per transformer block), but not per-token. The gate produces one weight vector per layer for the whole sequence.
  • Input to the gate: not the hidden state directly. Instead, the gate sees the concatenated outputs of all LoRA experts at that layer: $\{E_{\Delta\theta_i}(x)\}_{i=0}^{N}$. So the gating decision at layer $\ell$ is conditioned on what the experts would produce, not on a generic hidden state.
  • Pooling: the paper concatenates expert outputs along their feature dimension, flattens, and projects via a learnable matrix. Effectively a learned aggregation across experts; no temporal pooling.
  • Training loss: task loss + a balancing loss that explicitly discourages collapse:
$$ \mathcal{L} = \mathcal{L}_D + \alpha \mathcal{L}_{\text{balance}}. $$

1.4 Token-level LoRA adaptation (Belofsky, 2023)

Source: arXiv 2311.10847.

An interesting outlier — gradient-free routing. No trained gate at all.

  • Pre-compute a centroid embedding $a_k$ for each adapter's training dataset.
  • At inference, embed the prompt $\to p$. Compute cosine similarity to each centroid. Softmax.
  • The result is a per-prompt weighting that's static across the generation. (They tested re-computing it per token but that's optional.)
  • No pooling in the modern sense — they just embed the whole prompt with the model's existing sentence-encoder behavior.

This is essentially what your DESA could fall back to if learned routing keeps failing — pick adapter weights by similarity to per-cluster prototype embeddings.

1.5 LoRAHub (Huang et al., 2023)

  • Static routing — one weight vector per task, not per token, not per layer.
  • The weights are found by black-box optimization (Shiwa) on a few examples from the target task — no gradient through the LM.
  • No pooling, no per-input dynamic routing. Once tuned, the same combination is applied for the whole task.

1.7 What this means for DESA

You are the only one in this list mean-pooling. Among the modern LoRA-MoE methods, none collapse the sequence dimension before routing. Mean pool is more common in encoder-style classifiers (BERT-for-classification) than in generative-LM gating.

The actionable conclusions:

  1. Switch the pooling. If you must stay with a single $\alpha$ per turn, use last-token pooling on the causal-LM hidden state — that's much closer to how Mistral itself summarizes a sequence. Mean pooling over a 100-token EmpatheticDialogues prompt washes out the emotion signal entirely.
  2. Add a balancing loss. Every published method that doesn't collapse uses one. The pattern is
$$ \mathcal{L} = \mathcal{L}_{\text{CE}} + \alpha \, \mathcal{L}_{\text{balance}}, $$

where $\mathcal{L}_{\text{balance}}$ penalizes the gate either (a) for collapsing to uniform (entropy floor) or (b) for skewing too far from balanced expert use (load-balancing). Without one of these, gradient descent will find the lazy minimum where the gate is constant, exactly what your turn-gate did.

  1. Consider per-token routing for system 3. LoRAMoE-style — replace the mean-pool with a per-token softmax router, applied at the FFN of each block. You'd be much closer to the published recipes.
  2. For X-LoRA: load-balance loss + entropy regularization. The Buehler paper doesn't ship one but in practice every X-LoRA reproduction adds it, otherwise the classifier saturates to uniform — exactly your $H \approx \log 4$ result.

Part 2 — What "embeddings" actually means

You spotted a real source of confusion: "if input embeddings are just static lookup vectors that the model multiplies by attention, why do people talk about 'GPT-3 embeddings' as a thing you can use for classification?"

The answer: the word "embedding" is overloaded across at least three different things, and the one OpenAI sells via API is not the input lookup table. Let's untangle.

2.1 Three things called "embedding"

NameWhere it comes fromShapeUseful alone?
Input embedding (token embedding) Lookup table $E \in \mathbb{R}^{V \times d}$ at the very bottom of the model $(d,)$ per token, no context Mostly no — a static word2vec-like vector
Contextual embedding (hidden state) Output of layer $\ell$ in the transformer; varies with surrounding text $(d,)$ per token, context-dependent Yes — the actual semantic content
Text/sentence embedding A pooled or specially-trained vector summarizing a whole text $(d,)$ for the whole input Yes — that's the whole product

"GPT-3 embeddings" or "OpenAI's text-embedding-3-large" or "Cohere embeddings" all refer to the third kind. Not the lookup table.

2.2 Input embeddings: a learned lookup table

At the very bottom of any transformer there's a matrix $E \in \mathbb{R}^{V \times d}$ where $V$ is the vocabulary size (~32K for Mistral) and $d$ is the hidden size (4096 for Mistral-7B). Total parameters: $32K \times 4096 \approx 131M$.

The "embedding" of a token is just the row of $E$ at that token's index:

$$ \text{embed}(\text{token id } i) = E[i, :] \in \mathbb{R}^{d}. $$

That's it. No attention, no context. The vector for the token "bank" is the same whether the sentence is "river bank" or "Bank of America".

2.3 Are they parameters?

Yes — they're learned parameters during pretraining. Each row of $E$ is updated by gradient descent along with everything else. After pretraining ends and you're using the model for inference, the table is frozen, but the values in it were absolutely shaped by the optimization.

This is why your earlier intuition was almost right: at inference, the embedding lookup is fixed and "the embeddings don't change." But during pretraining they do change, and the values they end up at carry surprising amounts of information — pretrained input embeddings encode coarse semantic similarity (king − man + woman ≈ queen, the classic word2vec result, also approximately holds for transformer input embeddings).

So they're not "useless dummy vectors," they're more like a learned dictionary of "what each token roughly means in isolation." But they are very limited compared to contextual representations — they can't tell you that "bank" means river or finance based on the sentence, because they don't see the sentence.

2.4 Contextual embeddings: the actually useful kind

Once you push the input embeddings through the transformer's $L$ layers, each token's vector gets updated based on every other token in the input (via self-attention). The hidden state at layer $\ell$, position $t$, denoted $h^{\ell}_t \in \mathbb{R}^d$, is a context-aware summary of token $t$ and its surroundings.

Two sentences:

"I sat on the bank of the river." ▲ │ contextual embedding for "bank" │ ≈ vector close to "shore", "edge", "stream" "I deposited cash at the bank." ▲ │ contextual embedding for "bank" │ ≈ vector close to "money", "finance", "ATM"

The input embedding for "bank" is the same in both sentences. The contextual embedding from the top of the transformer is very different. That's the magic of attention.

2.5 "Text embeddings" sold by API providers

When OpenAI, Cohere, Anthropic, Google sell an "embeddings API" — say, text-embedding-3-large — what you get back is a single fixed-length vector for the whole input, not a $T \times d$ matrix.

Internally, the recipe is roughly:

  1. Take a transformer (often an encoder, sometimes a causal LM repurposed).
  2. Pass the input through all $L$ layers.
  3. Pool the contextual embeddings at the last layer down to a single vector. Common choices:
    • Last-token for causal LMs (the standard for GPT-style embedding models).
    • Mean pool for encoder models (the standard for many BERT-derived embedders like Sentence-BERT).
    • CLS-token for BERT (the special [CLS] token's hidden state).
  4. Optionally project / normalize. Often the model is trained with a contrastive objective (similar texts should have nearby vectors) so the resulting space is geometrically meaningful for cosine similarity.

So an OpenAI "embedding" is the mean-pooled (or last-token-pooled, or specially trained) contextual representation at the top layer of a model that was trained on a contrastive objective specifically to make its pooled output useful as a sentence vector.

This is precisely what your DESA gate could consume directly — if you wanted, you could call the model's last-layer hidden state with last-token pooling and use that as the gate's input. That's actually almost exactly what the Belofsky token-level paper does (§1.4), using cosine similarity between prompt embedding and centroid embeddings to route.

2.6 Why the naming is so confusing

The term "embedding" historically meant any mapping from discrete symbols to continuous vectors. word2vec, GloVe, FastText all produced static word embeddings — one vector per word, no context. ELMo, BERT, GPT introduced contextualized embeddings — one vector per word per occurrence. Sentence-BERT and OpenAI's embedding models then collapsed those into one-vector-per-sentence.

All three are "embeddings" in the original mathematical sense (a map into $\mathbb{R}^d$), but they're computed very differently and used very differently:

If someone says…They almost certainly mean…
"the model's input embeddings"The static lookup table $E$ at the bottom.
"contextualized embeddings" / "hidden states"The $T \times d$ output of some layer of the transformer.
"text embeddings" / "sentence embeddings" / "text-embedding-3-large"A single $d$-dim vector per input, pooled from contextual hidden states, often contrastively trained.
"using GPT-3 embeddings for classification"The third one. Not the input lookup.
The mental model. Input embeddings = a multilingual phrasebook (one entry per word, fixed). Contextualized embeddings = what a translator says the word means in this sentence. Text embeddings = a one-line summary of the whole conversation. Different things, different shapes, different uses.

Tying both halves together

The two questions actually share a thread.

  • Your DESA gate consumes a contextualized embedding pooled to a single vector — exactly the API-style "text embedding."
  • The literature has shifted strongly toward not pooling — routing per token (LoRAMoE, X-LoRA) gives finer control and avoids the very signal-dilution that's killing your gate.
  • If you want to keep mean pooling, you have to borrow the published anti-collapse trick: add a balancing or entropy-regularization term to the loss.

If you take one thing away: the routing literature does not pool, and when it does, it adds an auxiliary loss to keep the gate from collapsing. Your current setup does neither.
