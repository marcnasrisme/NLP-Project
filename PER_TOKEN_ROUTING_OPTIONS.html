1. The original DESA proposal vs the four routing granularities

The original DESA write-up specifies two routing systems:

  1. Turn-level blending (System 3): one $\alpha \in \Delta^3$ per conversation, applied at every layer for every token.
  2. Token-level blending (System 4): one $\alpha_t$ per token, applied at every layer.

That second goal — per token — is what we should be implementing. PEFT's XLoraConfig provided a convenient implementation, but X-LoRA actually does something more granular than the proposal asks for: per-(token, layer) routing. There's a hierarchy:

Granularity Routing tensor shape Decisions per example ($T \approx 80, L = 32, K = 4$) Where this lives
Per-conversation $(K)$ $4$ System 3 (your turn gate)
Per-token (proposal target) $(T, K)$ $\approx 320$ What System 4 was supposed to be
Per-layer (each layer routes the whole sequence) $(L, K)$ $128$ MoLE, LoRAMoE-style
Per-(token, layer) $(T, L, K)$ $\approx 10{,}000$ X-LoRA (PEFT default — what you actually instantiated)

Per-token routing is the missing middle. It gives every token its own routing decision but reuses that one decision across all 32 layers. The proposal asks for this; X-LoRA went one step finer; our pooled-CE training collapsed it back even coarser than per-conversation in practice.

2. Why both pooling-over-tokens schemes break per-token routing

You correctly identified that any objective that averages across tokens during training defeats per-token routing, regardless of whether it also averages across layers. Let's see why mathematically.

Pooling across $(t, \ell)$ — what we currently do

$$ \bar z = \frac{1}{T_{\text{real}} \cdot L} \sum_{t, \ell} z_{t, \ell}, \qquad \mathcal{L}_{\text{CE}} = -\log \sigma(\bar z)_y. $$

Per-position gradient: $\partial \mathcal{L} / \partial z_{t, \ell}$ is scaled by $1/(T_{\text{real}} L) \approx 1/2560$. Per-position softmaxes never sharpen — confirmed by our entropy plateau at 1.38.

Pooling across $t$ within each layer (option 3 from the previous explainer)

$$ \bar z_\ell = \frac{1}{T_{\text{real}}} \sum_{t} z_{t, \ell}, \qquad \mathcal{L}_{\text{per-layer}} = \sum_{\ell=1}^L -\log \sigma(\bar z_\ell)_y. $$

This sharpens per-layer averages but still pools tokens, so every token within a layer can be diffuse and the average can still match. It buys per-layer specialization at the cost of throwing away per-token specialization.

Your point, restated formally: any objective whose gradient per position scales as $1/T_{\text{real}}$ or smaller will leave per-token routing diffuse. To force per-token sharpness, the gradient at each position must be $O(1)$, not $O(1/T)$. That is only achievable if every token contributes its own CE term to the loss, not merely a fraction of one.

3. The actually viable options for per-token routing

Given the proposal's "per-token" target and the constraint that we have only conversation-level labels, the supervision must look like:

$$ \mathcal{L}_{\text{per-token}} = \frac{1}{T_{\text{real}}} \sum_{t=1}^{T_{\text{real}}} -\log \sigma(z_t)_y $$

where $z_t \in \mathbb{R}^K$ is a routing logit per token (no $\ell$ index — same $z_t$ used at every layer). Each token contributes a full-magnitude CE gradient; per-token softmaxes will sharpen.

Now the only remaining design question: what feature do we feed the classifier to produce $z_t$? This is exactly the dichotomy you identified.

Variant Classifier input for token $t$ Forward-pass cost Information used
Option A — last layer only $h^L_t$ (vector in $\mathbb{R}^d$) 1 forward pass; only top hidden state needed Top-of-stack semantics; everything Mistral has aggregated about token $t$ via 32 attention layers
Option B — pool over layers per token $\text{pool}(h^1_t, \dots, h^L_t)$ 1 forward pass; all hidden states cached Multi-resolution view of token $t$ across the depth of the network

You're right that these are the two viable options that respect the proposal's per-token routing intent.

4. Option A — last-layer per-token features

Mechanism

  1. Run Mistral once with adapters disabled; collect $h^L \in \mathbb{R}^{T \times d}$ (no pooling).
  2. Apply a small MLP gate row-wise: $z_t = g(h^L_t) \in \mathbb{R}^K$ for every $t$.
  3. $\alpha_t = \sigma(z_t)$ — per-token routing weights.
  4. At every layer $\ell$, the LoRA delta applied to token $t$'s projection is $\Delta W^{(\ell)}_t = \sum_k \alpha_{t, k} B^{(k, \ell)} A^{(k, \ell)}$. The same $\alpha_t$ is reused at all 32 layers.

Loss

$$ \mathcal{L}_A = \frac{1}{T_{\text{real}}} \sum_{t=1}^{T_{\text{real}}} -\log \sigma\!\left(g(h^L_t)\right)_{\!y}. $$

Pros

  • Clean. The gate sees Mistral's richest representation of each token — what the model "thinks" of it after full contextualization.
  • Per-token gradient is $O(1)$, not $O(1/T)$: per-token softmaxes will actually sharpen.
  • Identical training infrastructure to the turn-level gate; only the pooling step changes (last-token → all-tokens), and the loss aggregates per-token CE.
  • Memory-efficient: only the last hidden state is needed, no caching across layers.

Cons / open questions

  • Using top-of-stack semantics ($h^L_t$) to control routing at all layers is a temporal inversion: you've decided what the bottom layer should do based on what the top layer thinks. In practice this is fine — h^L_t encodes a posterior view of the token that's strictly more informative than h^1_t. X-LoRA's classifier reads from layer-$\ell$ to control layer-$\ell$, but it pays for this with a much larger feature space.

5. Option B — layer-pooled per-token features

Mechanism

  1. Run Mistral once; cache $h^1_t, h^2_t, \dots, h^L_t$ for every token $t$ (output_hidden_states=True; you already do this).
  2. Choose a layer-pooling: mean across all 32 layers, last-$K$ layers, or weighted average. Call the result $\tilde h_t \in \mathbb{R}^d$.
  3. Apply MLP gate: $z_t = g(\tilde h_t)$, then softmax.
  4. Apply $\alpha_t$ at every layer for token $t$, exactly as in Option A.

Three concrete sub-variants for "pool"

Sub-variantDefinitionNotes
B1. Mean over all layers $\tilde h_t = \frac{1}{L} \sum_{\ell=1}^L h^\ell_t$ Symmetric, simple. Loses the ordering of depths.
B2. Mean over last 4 layers $\tilde h_t = \frac{1}{4} \sum_{\ell=L-3}^L h^\ell_t$ Common BERT-derived embedding recipe; bias toward semantic layers.
B3. Concatenate $\tilde h_t = [h^1_t \,|\, h^2_t \,|\, \cdots \,|\, h^L_t] \in \mathbb{R}^{Ld}$ Most information; classifier input becomes 32 × 4096 = 131K dim, head ~~50× bigger.

Loss

Same per-token CE as Option A:

$$ \mathcal{L}_B = \frac{1}{T_{\text{real}}} \sum_{t=1}^{T_{\text{real}}} -\log \sigma\!\left(g(\tilde h_t)\right)_{\!y}. $$

Pros

  • The gate sees the full depth profile of each token. Useful when low-level surface form (which is what early layers encode) carries emotional cues that later layers smooth out.
  • Concatenation (B3) preserves all information.

Cons

  • Requires keeping all 32 hidden states resident in VRAM during the forward pass. For Mistral-7B at FP16 with $T = 512$: $32 \times 512 \times 4096 \times 2$ bytes $= 128$ MB per example, manageable but non-trivial.
  • Empirically: in encoder embeddings literature, "mean of last 4 layers" rarely beats "last layer alone" by enough to justify the complexity. Same is likely true for routing.
  • B3 (concatenation) blows up the classifier head size. With a 1024-dim bottleneck: $131K \times 1024 \approx 134M$ params just for the first layer — comparable to one full LoRA expert.

6. Option C — the X-LoRA paper's NTP approach (not what you proposed)

For completeness, since you mentioned it: the X-LoRA paper (Buehler & Buehler 2024) does not supervise the routing classifier with cluster labels at all. They train it with the standard next-token-prediction loss, with the X-LoRA stack live during the forward and backward passes:

$$ \mathcal{L}_{\text{NTP}} = -\sum_{i=1}^{N} \log p_\theta\!\left(y_i \mid y_{Per-position routing pattern emerges from optimization — each routing decision affects the LM loss, gradients flow back through the X-LoRA stack to the classifier. You correctly noted this is "very smart but unrelated to the options we had envisioned." It is a different paradigm: routing as a means rather than as a target.

This is the most general and most expensive of all options: full backward pass through 32 transformer layers per training step. With our QLoRA-frozen base it's also infrastructurally awkward (X-LoRA needs FP16 not 4-bit; gradients through the FP16 base are memory-hungry).

If you ever wanted to use it, the recipe is fully orthogonal to A and B: same per-token classifier architecture, completely different loss. Your design intuitions about per-token routing don't conflict with NTP loss; they just live at different parts of the optimization stack.

7. The supervision question: does per-token CE against a conversation label make sense?

One subtle objection to A and B both: with per-token CE against a single conversation-level label, the supervision is asking every token in the conversation to route to the same gold cluster. Doesn't that homogenize routing and defeat per-token expressivity?

Answer: in this dataset, no. EmpatheticDialogues assigns one emotion label per dialogue, and that label is meant to characterize the whole conversation. A "sad" dialogue is sad throughout, not just at one position. So asking every token to route to the gold cluster is the right inductive bias for the dataset we have.

The per-token mechanism still gains expressivity, just not from within-conversation positional variation. It gains from:

  1. Confidence modulation. A neutral filler token like "I see" produces an $h^L_t$ vector with weak emotional signal; the gate will produce a softer $\alpha_t$ for it (lower max-probability). An emotionally salient token like "devastated" produces a confidence spike. The aggregate routing across the conversation thus weights emotionally informative tokens more.
  2. Cross-conversation specialization. Different conversations route to different cluster mixtures; tokens within each conversation track that conversation's gold cluster. This is strictly more expressive than turn-level routing because the per-token confidence varies within each conversation, even if the direction is shared.
The honest read: with conversation-level labels, per-token routing's directional degree of freedom is wasted (every token aims at the same cluster), but its magnitude degree of freedom is real (some tokens are more confidently routed than others). This is still a meaningful gain over turn-level routing for tasks where token-level emotional intensity varies — which is exactly EmpatheticDialogues.

8. Verdict and recommendation

Your reasoning, scored

Your claimVerdict
"Pooling over tokens over layers defeats the purpose" Correct — gradient per position scales as $1/(TL)$, no per-position sharpening.
"Pooling over tokens in each layer would also defeat the purpose" Correct for the goal of per-token routing (it would deliver per-layer routing, a different architecture).
"Each token in last layer as predictor" is viable Correct — this is Option A. Per-token CE delivers $O(1)$ gradient per position; routing sharpens.
"Pool over the same token across layers, then gate" is viable Correct — this is Option B. Same convergence properties as A; richer features at higher memory cost.
"X-LoRA paper approach is smart but unrelated" Correct framing. NTP loss lives at a different layer of the design stack and operates on routing as a means, not a target.

What to actually build

Recommendation: implement Option A.
  • Same MLP architecture as your turn-level gate ($4096 \to 1024 \to 4$, ReLU, dropout).
  • Apply it row-wise to $h^L \in \mathbb{R}^{T \times d}$ instead of pooling first; produces $z \in \mathbb{R}^{T \times K}$.
  • Loss: per-token CE against the conversation cluster label, summed/averaged over real tokens (ignore padding via the attention mask).
  • At inference, apply $\alpha_t = \sigma(z_t)$ at every layer for token $t$ via PEFT's per-token weighted-adapter API (or a small custom hook if PEFT's API doesn't expose per-token weights cleanly).
  • Save as outputs/token_gate_v2.pt; add a System 5: token_level_v2 entry to the eval table.

Why A over B

  • $h^L_t$ already integrates 32 layers of attention; it's a posterior view of token $t$ that's typically richer than any combination of earlier layers.
  • B's marginal benefit is small in the "embedding from a frozen LM" literature; the engineering cost (memory, classifier size) is real.
  • A is the minimal viable variant that honors the proposal's per-token routing intent. Build A first, measure, and only escalate to B if A clearly underperforms.

The one infrastructure caveat

PEFT's set_adapters(weights=[...]) applies the same weight vector to every position in the sequence. To apply per-token $\alpha_t$, you have to either (a) call generation token-by-token with each $\alpha_t$ pre-computed (works, slow), (b) write a custom forward hook on each LoRA module that broadcasts an external per-token weight tensor across positions, or (c) use PEFT's X-LoRA infrastructure but configure it to share routing across layers (collapsing $(T, L, K)$ to $(T, K)$ via layerwise_scalings=False). Option (c) is the cheapest and reuses the most existing code.

Your reasoning was correct on every point. The proposal's "token-level blending" is a per-token concept, not the per-(token, layer) thing X-LoRA gives you, and not the conversation-level thing the current pooled-CE training collapses to. Options A and B are the right family. Option A is the minimum viable build.
